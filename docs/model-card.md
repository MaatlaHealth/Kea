# Model card: referral non-attendance

> **This model is experimental. It is trained on synthetic data generated by
> this repository. It has not been validated against real patients and must
> not inform patient care.**

## Summary

| Field | Value |
| --- | --- |
| Name | `referral-non-attendance` |
| Task | Binary classification: will a booked referral appointment be attended? |
| Served algorithm | Logistic regression with standardisation |
| Comparison algorithm | Histogram gradient boosting, trained but not served |
| Feature set version | `referral-attendance-v1` |
| Training data | Synthetic, generated by `kea_prediction.synthetic` |
| Trained on real data | No |
| Clinically validated | No |
| Default state | Disabled |
| Licence | Apache 2.0, with the rest of the project |

## What it is for

Referral coordinators cannot telephone everyone. This model is intended to
help rank which open referrals get attention first, by estimating how likely a
booked appointment is to be missed.

## What it must not be used for

- It does not diagnose anything.
- It does not predict a clinical outcome, and nothing in it relates to
  maternal or neonatal mortality or morbidity.
- It does not set or influence clinical urgency. Priority on a referral is a
  clinician's judgement and the model never touches it.
- It never changes what a patient is told. No message content, no appointment
  decision and no portal text depends on it.
- It is not a triage tool, and it must not be used as one.

## Why logistic regression is the served model

A coordinator looking at a score is entitled to an answer to "why". For the
logistic baseline, the contribution of each feature is the standardised
coefficient multiplied by the standardised value: a faithful account of how
this model reached this score, not a post hoc approximation. The gradient
boosted model is trained for comparison and is not served, so the product
never shows a score it cannot explain.

## Features

Eleven features, all derived from referral workflow data.

| Feature | Meaning |
| --- | --- |
| `lead_time_days` | Days between the appointment being booked and the appointment date |
| `travel_distance_km` | Straight line distance between the referring and receiving facilities |
| `priority_rank` | Referral priority: routine 0, urgent 1, emergency 2 |
| `prior_missed_appointments` | Appointments this patient did not attend in the past |
| `prior_attended_appointments` | Appointments this patient did attend in the past |
| `facility_missed_rate` | Share of past appointments at the receiving facility that were missed |
| `acknowledgement_delay_hours` | Hours between submission and acknowledgement |
| `appointment_weekday` | Day of the week, Monday is 0 |
| `reschedule_count` | Times this referral has been rebooked |
| `has_contact_number` | Whether a usable phone number is on record |
| `appointment_message_delivered` | Whether the appointment message reached the patient |

### Excluded by design

Age, race, income, marital status, HIV status, diagnosis, reason for referral
and every other clinical or protected characteristic. They are excluded even
where they might be predictive. A model that tells a coordinator to chase
people harder on the basis of who they are, rather than what the service did,
would be worse than no model.

`travel_distance_km` is the distance between two facilities, not between the
patient's home and anywhere. Kea stores no home coordinates.

### Versioning

The feature set version is sent with every request. The application rejects a
response whose version does not match, so the two cannot silently drift apart.
Changing the list, the order or the derivation of any feature requires a new
version string.

## Training data

`kea_prediction.synthetic` generates the data. It draws features from plausible
operational distributions and then draws the label from a logistic function of
those features plus noise.

The relationships it encodes are assumptions the authors chose:

- a longer wait between booking and the appointment increases non-attendance;
- greater distance between facilities increases it;
- previous missed visits predict further missed visits;
- previous attended visits predict attendance;
- a delivered appointment message reduces non-attendance;
- no contact number increases it;
- weekend appointments are missed more often.

These are stated here so nobody mistakes a learned coefficient for a finding.
A model trained on this data demonstrates that the pipeline works. It says
nothing about real patients.

## Evaluation

```bash
cd services/prediction
python -m kea_prediction.train --rows 8000
python -m kea_prediction.evaluate --rows 2000
```

Evaluation generates fresh data with a different seed from training, so the
model is not scored on rows it has seen. The report includes ROC AUC, average
precision, Brier score, a confusion matrix at the chosen threshold and a
calibration table.

**Any figure this produces is a property of the data generator.** It is not
evidence of clinical effectiveness and must not be presented as such. The
test suite deliberately does not assert a performance threshold, because a
passing threshold on synthetic data would give false assurance.

## How a score is presented

When the service is enabled, a referral shows:

- the score as a percentage, with a band in words;
- the main contributing factors, each with its direction;
- the names of any features that had to be imputed, with a note that the
  estimate is less reliable;
- the model name and version;
- whether it was trained on real data;
- whether it has been clinically validated;
- when it was last calculated.

It is rendered inside an "Experimental, not validated" panel, visually
separate from clinical information, and never beside the priority control.

## Missing inputs

A missing feature is imputed from a documented default and reported back. It
is never silently replaced with zero, because zero is a meaningful value for
several of these features.

## Monitoring in a deployment

The service logs, per request, the model name, the version, how many inputs
were missing and the duration. It never logs a feature value, because a
feature vector plus a timestamp can identify a referral.

Before relying on a model in any setting, an operator should track:

- the distribution of scores over time, for drift;
- the realised non-attendance rate against the predicted rate, for
  calibration;
- the missing feature rate, which rising indicates upstream data quality
  problems;
- the rate at which coordinators act on high scores, which measures whether
  the model is useful rather than merely accurate.

None of that monitoring is implemented in this repository. The design is
documented; the implementation is outstanding.

## Turning it off

Set `PREDICTION_ENABLED=false`, or remove `PREDICTION_SERVICE_URL`. Existing
stored predictions remain visible with their model version and timestamp, and
no new ones are calculated. Every screen works.

## What validation would require

Before a score could responsibly influence anything:

1. A labelled dataset from the deploying service, large enough and
   representative of its population.
2. Evaluation on a held out period, not a random split, because attendance
   behaviour is seasonal and service changes shift it.
3. Subgroup analysis for disparate performance, including on characteristics
   the model does not use.
4. Prospective silent running, comparing predictions with outcomes before
   anything is shown to staff.
5. A clinical and information governance review of the intended use.
6. A monitoring plan with defined thresholds for withdrawing the model.

None of this has been done.
